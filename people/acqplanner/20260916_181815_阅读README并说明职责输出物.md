检查结果：**源数据中的播报文本没有前导空格，但渲染后的文本列确实存在对齐不一致，属于格式化问题。**

原因是生成器使用：

```python
f"{time_s:02d}s   {speech}"
```

时间只规定“至少两位”，不是固定宽度：

```text
30s   插枪
150s   稳定充电观察开始
```

因此：

- 两位秒数后的播报首字符位于第 7 列；
- 三位秒数后的播报首字符位于第 8 列。

相关实现位于 [acquisition.py:153](/Users/hwy/Castle/people/acqplanner/src/acquisition.py:153)。

检查两份 `.source.json` 后，所有 `speech` 字段的前导空格均为 0；生成的事件行自身也都从时间字符开始，没有行首缩进。也就是说，问题不是播报文字被写入了空格，而是时间字段长度变化导致播报列左右移动。若下游按固定字符位置截取播报内容，还可能把分隔空格带入播报文本。当前尚未修改文件。

规则如下：

- 再添加固定的 3 个分隔空格；
- 所有播报首字符固定在第 9列；
- 所有缩进说明也固定使用 8 个前导空格；
- 校验器检查时间上限和每行的精确起始列。

生成逻辑可改为：

```python
time_field = f"{time_s:02d}s".ljust(5)
event_line = f"{time_field}   {speech}"
note_line = f"        {note}"
```

这样既保留现有 `00s` 表达，又能在一小时以内保证播报和说明严格对齐。下游仍应按“时间字段 + 空白 + 播报文本”解析，而不应把分隔空格当作播报内容。

- `AGENTS.md`
- `README.md`
- `manifest.yaml`

- `context/`

跨 Person 工作不通过相互进入目录完成，而是通过 Castle 管理的交接区或服务完成，例如：

Planner只能执行类似：

```text
submit(

  artifacts = [...],
  hashes = [...],
  audit_request = ...
)
```

提交后：

- 系统生成不可变 `submission_id`；
- 保存提交时间和提交者真实身份；
- 锁定被审文件或内容摘要；
- 将成果置于 Auditor可领取的队列；
- Planner不能进入 Auditor工作区；
- Auditor也不需要进入 Planner内部目录。

每个 Person只公开最小协作接口，例如：

```text
Identity
Produces
Accepts
Submission requirements
Result types
```

`PERSON.md` 可以承担一部分公开职责说明，但不应暴露内部 manifest 或运行配置。

- Auditor接受什么；
- 应提交哪些材料；
- 正式结果如何返回。

- `read`：只读挂载；

- 跨 Person 写入：原则上禁止；
- Submission 和 Audit Result：通过受控 API，而不是直接编辑对方文件。
