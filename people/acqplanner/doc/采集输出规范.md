# 采集输出规范

本规范用于保证 Acquisition 在 macOS、Windows 或其他工作环境中使用一致的生成过程和内容质量。

## 1. 单一来源与输出

每个 Acquisition 在 `work/` 中使用一份同名 `.source.json` 作为生成源。Source 以 `artifact_metadata` 记录对应成果的 Artifact Metadata，由 `src/acquisition.py render` 确定性生成：

- `.txt`：现场执行脚本；
- `.md`：脚本不适合承载的简洁执行说明。

`.md` 由生成器写入 Artifact Metadata；纯现场 `.txt` 不内嵌元数据。

不手工分别维护两份输出。需要调整时，修改 `.source.json` 后重新生成和校验。

## 2. 文本稳定性

- 编码：UTF-8，无 BOM；
- 换行：LF；
- Unicode：NFC；
- 缩进：空格，不使用 Tab；
- 行尾：不留空格；
- 文件末尾：保留一个换行；
- 时间：使用 `0–9999s` 范围内的整数秒，从 `00s` 开始并严格递增。

## 3. `.txt` 脚本

`.txt` 不写文档标题、采集条件或表头。每个时间点的结构是：

```text
30s     插枪
        将交流充电枪完全插入充电口
        插入后等待车辆自然建立充电
```

第一行是事件文本，可直接用于文本转语音，不加“播报”和引号。后续缩进行是当时状态、现场操作或必要说明，不作为播报文本。

事件文本应简短、直接，优先使用一听就能执行的动作短语，例如 `插枪`、`停止充电`、`拔枪`。车型无关的必要限定和解释放在缩进说明中，不把播报句写成长句。

现场取证必须在事件文本中明确说出动作，例如 `拍摄充电数据`、`录制异响`、`记录仪表数值`。不用含糊的“确认某状态”代替拍照、录音或记录动作。缩进说明再写清取证对象和必须可辨认的信息。

为保证脚本便于人工阅读，时间字段占 5 个字符，不足部分在右侧补空格，其后使用 3 个分隔空格。事件文本和缩进说明统一从第 9 列开始：

```text
00s     两位秒数事件
150s    三位秒数事件
9999s   四位秒数事件
        缩进说明与事件文本对齐
```

采集边界使用以下固定规则：

- `00s` 的事件文本永远是 `开始采集`；
- 采集前必须满足的初始状态、设备准备或其他说明，写在 `00s` 的第二行及后续缩进行中；
- 最后一个时间点的事件文本必须是 `停止采集`；
- 如果停止后还需要保存、命名、核对或其他收尾提示，将它们写成 `停止采集` 事件下的缩进说明，不再增加后续时间点。

例如：

```text
00s     开始采集
        确认初始状态成立
        确认采集设备已就绪

30s     插枪

90s     停止采集
        保存并核对本次采集文件
```

## 4. `.md` 说明

`.md` 只写完成当次采集所需的补充内容，例如：

- 必要的执行条件；
- 时间顺延原则；
- 现场必须知道的注意事项。

不重复整份时间轴，不写成长篇 Acquisition Plan 或分析文档。

## 5. 内容边界

通用汽车知识可用于设计通用控制过程，但不得自行写入车企、品牌、具体车型、品牌 App、专属按钮或界面路径。现场操作应写成功能性、车型无关的表达。

如任务确实必须使用特定车型操作，必须先有项目内或 manifest 允许资源中可追溯的依据，并由用户明确确认。

## 6. 生成与校验

```text
python src/acquisition.py render work/NNN-名称.source.json --output-dir work
python src/acquisition.py check work/NNN-名称.source.json --output-dir work
python -m unittest discover -s src/tests
```

`render` 会生成两份输出；`check` 同时校验源文件、输出格式和生成结果是否一致。

正式送审前必须先完成两项 Planner 质量控制：

1. **形式自检**：运行单元测试和 `check`，确认文本格式、生成结果和内容边界符合规范。
2. **内容自审**：由 Planner 对照任务目的，检查目标覆盖、步骤必要性、单人可执行性、时序、后续分析线索和资料边界，并在同名 `_SelfAudit.md` 中留下结果。

两项都通过，只表示当前成果具备正式送审条件；成果仍保持 `DRAFT`。Planner 还必须按 `doc/Acquisition工作约定.md` 在同名 `_Audit.md` 中完成 Formal Submission，以 SHA-256 锁定本次被审的 `.source.json`、`.txt` 和 `.md`，并将 Submission 实际交付给 Independent Auditor。完成该明确动作后，成果才进入 `TO_AUDIT`。

这些步骤不替代 Auditor 对实验设计的独立判断，也不能产生 `CONFIRM`。
