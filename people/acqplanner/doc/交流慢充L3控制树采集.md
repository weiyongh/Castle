# 交流慢充 L3 控制树采集

**来源：** Notion
**页面：** 新能源汽修L3学习-交流慢充

## 一、简述

本文基于“新能源汽修L3学习-交流慢充”中的交流慢充控制树，整理正常交流慢充全过程中值得观察和验证的控制对象。

按以下阶段组织：

**插枪 → 慢充 Ready → 充电建立 → OBC 功率转换 → 电池状态 → 慢充结束**

这些内容用于帮助理解和实例化控制树，并为具体 Acquisition 提供参考。

**本文不是一次具体 Acquisition 的采集动作清单。**

表中的“必须 / 非必须”描述的是控制树层面的观测重要性：

* **必须**：确认当前控制关系时的重要观察对象。
* **非必须**：具有控制或诊断价值，但不是确认当前控制关系首先需要关注的对象。

这里的“必须”**不表示每一次 Acquisition 都必须通过现场操作取得该项信息**。

具体一次 Acquisition 采什么、怎样采，以及是否需要额外操作取得某项信息，由该次采集目的决定。

例如，某项故障状态可以是理解或诊断控制节点时的重要 Evidence，但如果当前任务只是取得一次正常慢充全过程 CAN 数据，并不因此自动产生“读取 DTC”的现场操作。

## 二、术语说明

| 术语         | 定义                                                                                         |
| ---------- | ------------------------------------------------------------------------------------------ |
| `number`   | 数值型 Signal。数值可以为整数或小数，可具有明确物理单位，如 A、V、kW、℃、% 等。                                            |
| `status`   | 状态型 Signal。底层可以表现为 Bool 或 Enum，用于表示当前控制节点或系统所处状态。                                          |
| `request`  | 请求型 Signal。表示控制器发出的控制意图或控制请求。                                                              |
| `feedback` | 与某一 `request` 对应的执行结果或反馈 Signal。与对应 Request 应存在较强关联，并具有符合控制过程的时序关系，即 `request → feedback`。 |
| `fault`    | 与当前控制过程有关的故障状态 Evidence。DTC 可以是判断这种状态的一种证据来源。                                              |
