## 助手

我把这套采集规范理解为：它定义了 CANVoiceRunner 单次采集 Session 的“事实索引合同”，用于把现场发生的事件、时间、照片、备注和录音组织成可校验、可追溯、可供后续 ASC 分析使用的数据。

它不是 CAN 原始数据本身，也不负责得出车辆状态或诊断结论。

### 1. 数据的核心作用

一次导出的 JSON 主要回答：

- 这次 Session 何时开始、何时结束、是否正常完成；
- 脚本计划了哪些 Event；
- 各 Event 实际何时触发，是否被跳过；
- 哪些照片属于哪个 Event，拍摄时间是什么；
- 现场人员留下了哪些备注，备注是否被修改或逻辑删除；
- 是否启用了录音，录音是否保存成功及其时间边界；
- 上述记录如何与 Session 的统一时间轴对齐。

它更像一份“现场事实目录和时间线”，用于索引随包提供的 ASC、照片及音频附件。

### 2. 时间体系是分析的主轴

规范同时记录两类时间：

- `*_clock`：带日期、毫秒和时区的现实世界时间；
- `script_time_us`：以 Session 正式开始为零点、基于 `ELAPSED_REALTIME` 的整数微秒时间。

后续分析主要可以用 `script_time_us` 把 Event、照片、备注与 ASC 时间窗口关联起来；Clock 则用于跨文件核对和现实时间追溯。

录音比较特殊：它可能在 Session 正式开始前启动，所以 `request_offset_us` 和 `start_offset_us` 可以为负数。微秒只是存储分辨率，不代表现场事件真的具备微秒级准确度；录音起点还明确记录了工程误差，例如 `start_accuracy_us = 20000`。

### 3. Session、Event 和附件的关系

整体关系是：

```text
Session
├─ Events
│  ├─ Photos
│  └─ Event Notes
├─ Photo Notes
└─ Audio Recording
```

但必须注意：

- Photo 通过 `event_id` 明确关联 Event；
- Note 通过 `target_type + target_id` 关联 Event 或 Photo；
- Audio 只属于整个 Session，不自动关联某个 Event；
- 时间接近不能自行升级为对象之间的正式关联。

这对分析很重要：我可以说某段录音与某事件时间上接近，但在没有额外 Evidence 时，不能宣称录音内容一定属于该事件。

### 4. Event 保存“计划”与“实际”两套事实

每个 Event 同时包含：

- 原始动作与说明；
- 原始计划时间 `plan_time_s`；
- 实际状态；
- 实际触发或跳过时间。

提前、延迟、暂停或跳过都不能改写原计划。尤其是 `skipped` Event，仍然保留触发时间和跳过确认时间。这使分析能够区分：

- 脚本本来要求什么；
- 播报实际何时发生；
- 现场是否确认不执行；
- 实际执行是否偏离原计划。

### 5. 现场记录尽量保留原始事实

规范倾向于保留事实，而不是静默修饰数据：

- 拍照失败不创建虚假的 Photo 占位；
- 照片后来不可读时标记 `UNAVAILABLE`，但不删除原记录；
- Note 使用逻辑删除，删除后仍保留文本与历史时间；
- 空值使用真正的 JSON `null`，不以空字符串、`-1` 或伪造的 `0` 代替；
- 现场文件异常或校验失败时，应保留原文件并报告问题，不能静默修复。

这与 Analyst 的 Evidence 原则一致：异常本身也是需要保留的观察，不能为了获得“干净时间线”而重写现场事实。

### 6. 录音是附属 Evidence，不决定主 Session 成败

录音可处于：

`DISABLED / PREPARING / RECORDING / SAVED / FAILED / SAVE_FAILED`

录音失败不会自动导致 Session `FAILED`。因为它是可选附属 Evidence，不应阻断主采集流程。

但对分析而言，录音失败会降低某些现场动作或口述事实的可验证性。因此应将其记录为 Evidence 缺口，而不能据此否定其他采集数据。

### 7. 校验必须分两层

第一层是 JSON Schema 结构校验，检查：

- 字段是否完整；
- 类型、格式和枚举是否正确；
- Clock 和 ID 是否符合格式；
- 条件字段组合是否合法；
- 是否出现未定义字段。

第二层是 Schema 无法独立完成的语义校验，例如：

- ID 是否唯一；
- Event 顺序是否唯一且连续；
- Photo 和 Note 引用的对象是否存在；
- `photo_id` 是否与 `event_id` 一致；
- ISO Clock 与 Epoch 是否表示同一时刻；
- 各时间是否落在合理的 Session 范围；
- 修改时间是否晚于创建时间；
- 一张照片是否只有一条未删除备注；
- 附件是否真实存在且可读。

只有两层都通过，才能把 JSON 当作可靠 Timeline 输入后续分析。校验通过也仅表示记录结构和内部关系成立，不表示现场陈述、车辆状态或诊断结论已经被证明。

### 8. 我在分析中的使用边界

我会把其中不同信息分别看待：

- Event、时间戳、对象关系：结构化采集记录；
- Note：现场人员留下的陈述，不自动等于已经验证的事实；
- Photo：需要实际查看图像后才能形成视觉 Observation；
- Audio：需要读取或转写内容，并考虑起点准确度；
- ASC：需要独立解析，观察总线实际变化；
- 多种 Evidence 相互印证后，才能形成 Evidence-supported Conclusion。

因此，这份规范提供的是“证据怎样被组织和对齐”，而不是“证据最终说明了什么”。后者正是我作为牛猛需要完成、并接受独立审计的工作。
