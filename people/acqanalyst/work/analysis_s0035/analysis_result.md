现场补充条件：

- 本次充电由充电桩微信小程序扫码启动；E04 后还包含人工手机操作、小程序/网络交互和充电桩响应。
- 停止充电同样通过充电桩微信 App 完成；相较启动，结束操作响应更及时，但仍存在人机与外部系统时间误差。

- 采集期间驾驶车门打开，会引入与车门、座舱唤醒、UI或车身状态有关的 CAN 变化。

本分析从原始 CAN ID/Payload 出发，不预设 Signal。候选 CAN 字段仅以 `CAN ID + byte + bit` 或完整 Payload 表达，不声明正式 Signal 名称或物理语义。

ASC 共有 915,670 帧、279 个 CAN ID，文件时间范围为 `2026-09-17T13:24:06.000+08:00` 至 `13:30:50.968+08:00`。

### 1.1 方法先验与数据观察必须分开

本分析使用了两类程序，它们的证明能力不同：

1. `analyze_s0035_raw_can.py` 预先使用 Event Clock，并定义 Event 前 `[-5,-1] s`、后 `[+1,+5] s` 窗口、bit 占比变化阈值和最少帧数。它回答“哪些字段在 Event 附近变化”，不能独立证明变化是什么语义。
2. `analyze_s0035_phase_bits.py` 更强地预先定义了六个时间窗，并将它们命名为 `pre_plug / plugged_pre_charge / charging_stable / stopped_connected / unlocked_connected / unplugged`，还预先搜索“中间平台”和“首尾回归”形状。它只用于从大量字段中筛选符合既定假设形状的候选，不能用于证明这些阶段是 CAN 数据无监督地产生的。

因此，本报告必须区分：

- **数据直接给出的内容**：原始 Payload、具体翻转时间、持续时间、多个 ID 是否在相近时刻变化、某个 Payload 是否后来回归、照片可见读数和订单时间。
- **外部 Evidence 给出的内容**：Event 的动作名称和时间，照片中的充电/停止状态。
- **分析者预先放入的内容**：窗口位置、窗口宽度、稳定阈值、对称平台筛选条件以及阶段名称。
- **解释**：把数据段与“连接”“充电”“停止”等物理过程关联。解释只有在 Event、照片和 CAN 变化相互印证时才可能成为 Evidence-supported conclusion；筛选命中本身不构成证明。

## 3. Observation

### O1：照片直接证明稳定交流充电已经建立

E05 的多张照片在约 97 秒内持续显示约 221–222 V、32.2–32.3 A 和 7.15–7.17 kW。电压与电流乘积约为 7.14–7.17 kW，与显示功率一致。车辆屏幕与充电设施读数也相互接近。

这是外部物理 Evidence，不依赖 CAN 解释。

### O2：停止后枪仍连接

E07-P01 显示订单已经完成，同时充电枪仍物理插入车辆。订单页面记录开始 `13:24:57`、结束 `13:28:21`、总量 0.367 kWh。

因此“功率传输停止”和“物理断开”在本 Round 中是两个不同阶段。

### O3：原始 CAN 中存在稳定的连接平台

多个候选字段在 E03 附近进入新平台，并在 E09 后返回初始平台。例如：

| Candidate | 连接方向变化 | 断开方向变化 | 观察 |
|---|---:|---:|---|
| `0x21D byte0 bit3` | 14.621 s：0→1 | 360.444 s：1→0 | 全程仅出现这两个主翻转 |
| `0x2EC byte0 bit6` | 15.416 s：0→1 | 360.942 s：1→0 | 与连接阶段成对 |
| `0x228 byte3 bit0/1` | 15.327 s：0→1 | 360.853 s：1→0 | 两个 bit 同步 |
| `0x2AA byte0 bit6` | 15.370 s：0→1 | 360.898 s：1→0 | 与 `0x2EC` 同步 |
| `0x43D byte5 bit5` | 11.220 s：0→1 | 365.747 s：1→0 | 较早进入、较晚退出，可能属于分阶段过程 |

这些字段的共同结构支持“与连接生命周期相关”，但单轮 Evidence 尚不足以确定每个字段分别代表插枪检测、锁止、连接确认或其他子状态。

### O5：`0x21D` 完整 Payload 呈现多个长时间数据段

| 数据段 | 代表 Payload | 与外部 Evidence 对照后的解释 |
|---|---|---|
| A：ASC 初段 | `04 00 35 00 00 00 00 00` | Event 表示此时尚未执行 E03 |
| B：约 14.6–53.6 s | `4c 00 02 20 00 00 10 00` | 位于 E03 后、外部充电开始前，候选“连接未充电” |
| C：约 53.6–256.1 s | `2f 40 22 20 80 00 30 00` | 与订单开始/结束及充电照片一致，支持“充电相关平台” |
| D：约 256.8–360.0 s | `4c 00 02 20 80 00 10 00` | 位于停止后、E09 前；E07 照片显示枪仍连接，支持“停止仍连接” |
| E：约 360.5 s 后 | `04 00 35 00 00 00 00 00` | E09 后回归 A 值，候选“断开后回归” |

数据本身直接给出的是 A–E 的 Payload 变化与 A/E 回归；阶段名称不是 Payload 自带语义。B、C、D、E 的物理解释来自 Event、照片和订单时间的交叉对照。其中 D 与 B 仅部分相同，可能还存在历史、许可、锁止或其他子状态，但当前不能确定。

### O6：未发现主要 CAN ID 的明显发送频率启停

以 Event 前后 4 秒窗口比较，没有 CAN ID 达到两倍以上的稳定帧率变化条件。主要结构来自 Payload 状态变化，而不是报文是否开始或停止发送。

### O7：bit 级候选可压缩为少数同步变化簇

为避免把同一状态在同一报文内占用多个 bit、或在多个报文中重复表达误算成多份独立 Evidence，仅保留全 ASC 内恰好发生一对相反方向翻转的候选，再按起止时间各不超过 0.25 秒进行聚类。

| P2 | 4 bit / 1 ID | 14.621 s | 360.4438 s | `0x21D` 内部多个 bit 同时翻转 |

上述同步性说明 91 个“充电平台 bit 候选”不能视为 91 份独立证明。更合理的表示是少数共享变化源在多个报文/字段中的同步或分阶段传播候选。现有数据能给出先后关系，不能给出报文之间的因果方向。

### O8：连接包络包含充电包络

无论采用 P2/P4 代表连接平台，还是采用 C1 代表充电平台，充电区间都完整落在连接区间内部：

```text
初始
  → 连接相关变化簇
      → 充电相关变化簇进入
      → 充电相关变化簇退出
  → 断开相关变化簇
→ 回到初始类 Payload
```

以 `0x21D` 的代表变化计算，连接相关平台约在 14.621–360.444 秒，充电相关平台约在 53.623–256.137 秒。数据只证明时间嵌套；“连接是充电的前置条件”符合物理过程和 Event，但不能仅凭时序当作 CAN 字段间的因果证明。

### O9：充电建立和退出均表现为多步变化，而不是单一瞬时翻转

主同步组 C1 在约 53.5–53.8 秒进入，C3 在约 55.6–55.8 秒进入，`0x364` 在 56.673 秒进入，`0x132` 在 63.497 秒进入。退出侧也存在约 256.1–258.7 秒的传播范围。

这支持“整个充电系统过程存在多步变化”的结构性观察。但启动路径包含人工操作、小程序/网络和充电桩响应，停止也由桩端微信 App 发起，因此这些时间层次可能来自外部操作链、充电设施、车桩协议、车辆内部状态传播或它们的组合。不能把这些步骤直接解释为车辆内部许可、接触器动作或控制链延迟。

### O10：现有照片不足以确认任何 CAN 数值字段

在四张 E05 照片时刻，`0x21D` 和 `0x43D` 的代表 Payload 保持不变，符合状态类候选。`0x252 byte0` 随时间从 `0xbb → 0xc5 → 0xd1 → 0xd2`，但四个外部读数点中的电压、电流和功率几乎恒定，能量值与该字节增量也不足以建立稳定比例。

因此可以继续保留“某些报文包含动态量”的候选，但当前不能确认电压、电流、功率、能量或 SOC 的数值编码。

## 4. Evidence-supported conclusions

### C1：本 Round 的 Evidence 支持交流慢充已经建立、稳定传输、停止，并最终完成拔枪断开

支持 Evidence：

- 现场补充确认 E03/E09 对应直接执行的插枪、拔枪物理动作；E04/E06 对应桩端扫码启动和 App 停止流程；
- E05 照片显示稳定的交流电压、电流和功率；
- E07 照片显示订单完成且枪仍连接；
- CAN 中存在与上述阶段时间一致的连接平台和充电平台，并在结束阶段回归。

该结论不包含“E08 已精确验证充电口锁止机构完成解锁”；解锁完成时刻仍缺少独立 Evidence。

### C2：与充电运行相对应的候选 CAN 平台，与连接生命周期相对应的候选 CAN 平台，在时间上可以区分

订单结束及 E06 停止流程附近，第一组候选平台退出；第二组候选平台仍保持，直到 E09 拔枪后才回归初始值。该顺序与 E07-P01 的“订单完成但枪仍插着”照片相互印证。现有 Evidence 支持两组平台分别与充电运行、连接生命周期相关，但尚未确认任何字段就是正式的功率状态或物理连接 Signal。

### C3：`0x21D` 是当前最强的候选状态载体之一

`0x21D` 在一个报文中呈现多个长时间数据段和首尾回归，并与其他 ID 的同步变化相互印证；外部 Evidence 使这些数据段与连接、充电、停止过程形成合理对应。当前可以把它作为下一轮 Signal Validation 的高优先级候选，但不能把 `0x21D` 或其中某 bit 直接命名为已确认的充电状态 Signal。

### C4：当前候选形成少数高度同步的共变组，不能按 bit 数量视为彼此独立的 Signal 或独立 Evidence

多个 bit 在同一报文内同刻翻转，多个 CAN ID 又在 0.1–0.3 秒范围内同步进入或退出。现有 Evidence 足以支持“候选之间存在高度同步的共变关系”，并支持在后续验证中按少数时序簇处理，而不是把每个 bit 当成独立发现。

共同状态来源、冗余广播、跨控制器传播、网关转发或多个独立控制量受同一过程驱动，均仍是待区分的 Hypothesis。该结论也不表示这些报文变化由车辆首先发起；本 Round 的启动和停止命令来自充电桩侧人机流程。

## 5. Candidate / Hypothesis

- `0x21D byte0 bit3` 等字段可能属于充电枪连接生命周期状态。
- `0x21D byte0 bit0/bit5`、`byte1 bit6` 及与其同步的 `0x43D`、`0x252` 字段可能属于充电功率建立或充电运行状态。
- 53.5–56.7 秒的分阶段变化可能反映许可、接触器、功率爬升或状态传播过程；现有 Evidence 不能区分。
- E08 后约 3 秒，`0x25D`、`0x43D` 等出现变化，但在此之前还存在拍照、车门/界面等活动，且缺少独立锁止 Evidence，因此不能确认这些变化代表解锁。
- 驾驶车门保持打开，部分候选可能属于车门、座舱唤醒、UI或车身状态；仅因其出现在充电 Event 附近不能归入充电控制链。

## 6. Unknown / Evidence gaps

- 采集包内没有现场 Note；用户后续补充已确认本次为充电桩微信小程序扫码启动、桩端微信 App 停止。该补充解决了操作来源问题，但没有 App 点击、网络请求、充电桩受理和车辆侧实际执行的分别计时，仍无法拆分各环节时间。
- 没有锁止机构、指示灯状态或解锁确认的独立 Evidence，不能确认解锁相关字段。
- ASC 未覆盖 E01、E02 和 E11；E10 后只有约 2.8 秒数据。
- ASC `date` 头只记录到整秒；Event Clock 记录到毫秒。ASC 内部候选之间的相对先后精度较高，但 Event/照片与 ASC 的绝对对齐仍存在最多约一个整秒量级的起点不确定性，不能把跨设备毫秒差当作物理延迟定论。
- 没有 DBC 定义审计，所有 CAN 字段仍是 raw candidate。
- 单个 Round 无法排除某些同步字段是同一状态的转发、冗余表达或伴随状态。
- 驾驶车门打开构成持续混杂条件，当前不能系统排除车身/座舱状态候选。
- 照片提供稳定功率读数，但没有足够高频外部测量用于校准 CAN 中的电压、电流或功率数值字段。

## 7. 建议的下一轮验证需求

- 分离执行“插枪但不启动”“启动充电”“停止但不解锁”“解锁但不拔枪”“拔枪”，每阶段保持足够长稳定窗口。
- 在每个阶段拍摄充电口指示灯、锁止机构或明确 UI 状态，并记录实际操作完成时间。
- 分别从车辆侧和充电设施侧停止，验证当前候选状态是否具有相同或不同路径。
- 对 `0x21D`、`0x43D`、`0x252` 等候选进行跨 Round 重复性、方向性和物理闭环验证。
- 若要识别电压、电流、功率字段，增加同步外部测量点并覆盖不同电流档位，而不仅是稳定 32 A 单点。
